# Demo mode

The real app, running against a pretend broker and a made-up market, on one fixed day. Nothing in it is real money and nothing leaves the process. Why it's built this way: decision 0100.

## Running it
```bash
uv run python -m optionsjourney.demo --port 5099
```
Open http://127.0.0.1:5099. The runner starts the app in a child process with `BROKER_CREDENTIALS=demo` on an empty data folder (a temporary one, or `--data-dir`), on this computer only (`LISTEN_ON_NETWORK=no`) and reading no `.env` (`PYTHON_DOTENV_DISABLED`); the seats get the same environment from the same helper (`marker.demo_env`). A `--data-dir` must be empty or hold an earlier demo; the runner empties it and refuses anything else. Stopping the runner removes the temporary folder.

Setting `BROKER_CREDENTIALS=demo` by hand and running `python -m optionsjourney` works too, but then **Start a new day** only stops the app, because nothing is there to start it again. Use the runner.

## The demo day
- Wednesday 21 October 2026, starting at 9:40 New York time (`demo/clock.py`). The clock is moved for the whole process with `time-machine` and keeps ticking at normal speed, so every `datetime.now()` and `time.time()` in the app sees demo time.
- **Skip ahead** (a button in the banner) moves the clock 15 minutes, or to the close (16:00 New York). The engine steps at once, so fills and prices from the jump show immediately.
- At the close the pretend broker rings the bell once: Day orders expire and the day's expiring options settle. The banner then says "The demo's trading day is over" with a **Start a new day** button.
- **Start a new day** (`POST /demo/new-day`) shows a page, and when that response has closed a timer exits the process with code 75 (`NEW_DAY`). The runner sees 75, empties the folder and starts the app again, so the day is 9:40 with a fresh account. Any other exit code stops the demo with that code.

## How it works
- `app.py` builds the demo parts first when `settings.is_demo` (`_demo_parts`): installs both guards, the clock, the market and the pretend brokers, and builds the seed database. Every demo branch sits behind `settings.is_demo`, so local and gateway mode don't change.
- `market.py` and `levels.py`: a deterministic, seeded market. Pure Python; it never reads the clock. Option prices use a trading-time basis, so 0DTE marks look right.
- `broker.py` and `book.py`: a pretend TastyTrade (where trading happens) and Schwab (history, stock holdings, chart history). They return the same raw shapes as the real ones, so the app's own parsing and sync run unchanged. Working orders fill in `match`, which the engine calls with every tick the market moved through.
- `feeds.py`: quotes and candles into the app's real quote hub and chart feed. Its stream (`DemoStream`) keeps at most `MAX_KEYS` (1,500, about three SPX chains) quote keys, dropping the oldest subscribed first, but never part of the subscription being added: a chain arrives as one set in hash order, so cutting it would leave a different few strikes unpriced in each process. The bots' market filters read the pretend Schwab's market data only (`bot_loops._filter_feeds`): TastyTrade's filter stream is a socket, so demo mode never builds it. VIX9D has no path of its own: it is always VIX × `VIX9D_RATIO` (`levels.py`). `news.py`: made-up headlines with the source "Demo headlines".
- `engine.py`: one heartbeat. It moves the market to now, fills crossed orders, syncs fills into the journal and pushes prices. Tests drive `engine.step` themselves (with `TESTING`, no threads start).
- `seed.py` and `history.py`: the starting account. About thirteen weeks of made-up trades are written into the pretend accounts as each broker's raw records and brought in by the real sync. Three bots are saved through the bot store: SPX 0DTE condor (Live, Mondays, Wednesdays and Fridays; the history trades the days its schedule says), Weekly calendar (Live, open at the start) and QQQ put spread (Paper). The seed also saves one manual bot, "Put spread exits" (a 50% profit target and a 200% stop; `MANUAL_EXITS`), for the tour's hand-trade step. Past runs and exits that the app records only as a bot trades live are written as rows directly. Two builds are identical. The outcomes (`history.py`'s chances and `RNG_SALT`) are tuned so the history wins about 60–72% of trades with some losing weeks, and both Live bots the tour shows end a little ahead (`tests/demo/test_seed.py`).

## The staged moments (`director.py`)
The director only moves SPX. It places and changes no order.
1. **The 0DTE condor.** Once today's run has filled and its stops rest at the broker, SPX is pushed up, always toward the call side, just past the level where that stop triggers. It arrives about a minute (demo time) after the entry filled. The bot and the pretend broker then fill the stop and raise the alert as on any day.
2. **The calendar.** From 6 minutes after the start (or sooner, when the tour reaches step 5), SPX drifts toward the calendar's strike, just far enough for its resting 25% target to fill, then is let go.

The levels are found by pricing the exit's own legs with the pretend market. No move is faster than `MAX_POINTS_PER_MINUTE`, so a longer way takes longer. A calendar drift that comes due during the condor's push waits for it. If you change a bot's exit math or the seed, run `tests/demo/test_director.py`.

## The tour
A guided tour for first-time visitors: seven steps and a finish, shown in a box at the corner of every page. `demo/tour.py` is pure logic (`Tour`, `STEPS`, `TourFacts`, `DONE`); `tour_facts.py` works out the facts; `tour_trade.py` builds step 4's put spread; the routes are in `web/routes/demo.py`.

**Steps, and what completes each**
1. Your journal. Open Automation (`opened_automation`).
2. Arm a bot. Arm the SPX 0DTE condor (`condor_armed`).
3. The stop. The condor's stop fills and the visitor opens that run's page (`opened_condor_run` and `condor_stopped`).
4. Trade by hand. A put spread sent from the Trade page with Manage with = Put spread exits (the seed's manual bot, `MANUAL_EXITS`) and attached (`spread_managed`).
5. A profit target. The seeded Weekly calendar's target fills (`calendar_target_filled`). It fills about 6 minutes into the demo day, often before the visitor gets here, so this is the one step that doesn't count as done on arrival: reaching it after the target filled stops on it (held, like a step after Restart) with "…reached its profit target while you were trading" and a link to its runs, until Next. Reaching it before, the visitor watches it fill and the tour moves on.
6. Charts. The watchlist changes (`watchlist_changed`).
7. Build a bot. A bot of the visitor's own enters (`own_bot_entered`).
Then "That's the tour" with a link to the install page.

**Facts.** `facts(session_factory, visited, clock)` works out `TourFacts` from what happened (bot armed, today's condor run stopped, a per-trade bot with a run today, the seeded calendar's target filled, the watchlist changed, a bot of the visitor's own filled today), so a step counts however it was done. Only "opened Automation / the condor's run page" come from `Visited`, the tour pages a visitor opened (thread-safe; query strings dropped). `Tour.update` moves past every consecutive done step, so a visitor who did things out of order jumps ahead, except step 5 (above). It only moves forward, except Restart. Steps 2, 3, 5 and 7 show "The demo's trading day is over" once the day has closed, since they can no longer happen.

**Restart.** `restart(facts)` goes back to step 1 but *holds* the steps already done: they stay until the visitor presses Next past them (otherwise the next update would skip them all). A step whose fact becomes true after the restart still advances.

**Routes** (all in `web/routes/demo.py`, demo mode only; POSTs need the same origin as the app's pages):
- `GET /demo/tour`: the box's JSON (`step`, `total`, `title`, `text`, `link`, `link_label`, `highlight`, `finished`, `skipped`, `day_over`). Every call re-works the facts and may advance the tour.
- `POST /demo/tour/next` (`{"from": n}`: moves on only if still on step n), `/demo/tour/skip` (hides the tour), `/demo/tour/restart` (also what the banner's Restart tour form posts; it redirects back to the page).
- Reaching step 5 tells the director (`on_tour_step(5)`) to bring the calendar's target forward.

**The box** (`_demo_tour.html`, `static/js/demo_tour.js`, `demo.css`). It polls `GET /demo/tour` every 3 seconds and draws the step; a link is only an anchor if it starts with `/` (not `//`) or `https://`. It can point at a page element (`highlight`): always on steps 1 and 2, otherwise only on the page the step's link goes to. Escape hides the box until the next page load.

**The Trade tray** (`static/js/trade/tour_tray.js`). At step 4 only, the Trade page carries `data-tour-tray` on `#trade-ticket`: the two legs of `put_spread_tray` (short put near 15 delta, long put 25 points below, today's SPX expiration), shaped like the chain's own cells so the page drops them into the ticket.

**Measured timings** (a real browser run, for reference): at step 4, Review then Send with Manage with = Put spread exits fills and the tour moves to step 5 in about 6 seconds. The calendar's target fills about 150 seconds of real time after entering step 5 (the director drifts SPX at no more than `MAX_POINTS_PER_MINUTE`), which is why step 5's text says "about two minutes". `tests/demo/test_tour_end_to_end.py` drives the whole tour on the test clock in under 30 minutes of demo time.

## Safety
- **Offline guard** (`offline.py`): every `httpx` request, sync or async, and every `websockets` client connection raises `DemoOffline`, a `ConnectionError`, and logs a warning with the URL (so a route's own `except OSError` can't hide it).
- **Trading guard** (`brokers/guard.py`): installed as in gateway mode. It sits under every HTTP call and refuses anything that could trade. The pretend brokers never make such calls, so it's a second wall, not the only one.
- Neither guard can be switched off for the life of the process.
- **Demo databases are kept apart, both ways.** Demo mode builds its seed only into an empty folder, and refuses a folder whose database isn't marked as a demo's. Local and gateway mode refuse a database marked as a demo's (`_refuse_demo_data`). The mark and both refusals live in `demo/marker.py`, which imports nothing heavy: a local start reads it without loading the demo, and `python -m optionsjourney` checks it before it writes its log file, so a refused folder gets nothing written into it. A demo database has risk boxes ticked and a Live bot armed, so it must never open as a real app.
- Demo-mode text never says orders are real: the bot list, each bot's page, the arm pages, Preview order, the flashed messages and the Trade page say orders go to the demo's pretend broker. Templates use `demo_mode`; `bot_entry` reads `BotDeps.demo`; the Trade page's scripts read `data-demo` on `#trade-ticket` (`sendWarning`, `acceptedWords`, `sendLabel` in `trade_ticket.js`). Outside demo the text is unchanged. The help pages are the real app's guide and still describe real orders.

## What's switched off
Where the button would be, the page says "Not in the demo" (the `not_in_demo` decorator in `web/routes/demo.py`; an `/api/` call gets a 403):
- connecting or disconnecting TastyTrade and Schwab (in Settings and in the setup wizard's TastyTrade and Schwab steps), notification settings and their test, the backup folder, Back up now, Restore, and the calendar refresh (`settings.py`);
- installing an update (`update.py`);
- importing bots (`automation.py`).

Also off: scheduled backups, the update check, the market-calendar and Schwab-login threads (the calendar is stored once at the seed), and the account-stream listener (the engine syncs whenever something fills). Alerts show in the app instead of going to a notification service. News comes from `demo/news.py`, not Yahoo or Finnhub.

## Seats
The public demo gives each visitor their own copy of the app, a "seat" (decision 0102).
- **The seat manager** (`demo/manager.py`): `python -m optionsjourney.demo.manager --root <folder> [--port 8096 --cap 10 --warm 2]`. It isn't in demo mode itself. Its web side seats or queues visitors; a control loop thread every 2 seconds reads seat exits, checks each seat's health, and carries out the pool's actions. Stopping it (TERM or Ctrl-C) stops every seat.
- **The pool** (`demo/seats.py`): pure decisions, no I/O or clock. Seat n runs on port 5100 + n. It keeps `warm` seats ready when no one is waiting, starts more as people queue, and resets a seat after 20 minutes without activity, 60 minutes in all, three failed health checks in a row, or a start that takes over 60 seconds. A seat that crashes is started again after a back-off (10 s, 30 s, 1 min, 2 min, then 5 min). A seat that exits with `NEW_DAY` (Start a new day) is started again for the same visitor, with the same token. A queue place lapses after 2 minutes without a poll (browsers slow a hidden tab's timers to about once a minute).
  - **Warm seats age.** A seat's demo day starts when its process does, and the tour's staged moments follow it (the Weekly calendar's target fills 6 minutes in). So a warm seat no one has taken is restarted once it is 3 minutes old (`WARM_MAX_AGE`), oldest first and one at a time: only when no other unassigned seat is starting or stopping and 2 minutes (`WARM_STAGGER`) after the last such restart, so a warm seat is always ready. The turns go by age, not seat number, since a replacement takes whichever number is free. Waiting its turn never takes a seat past 5 minutes (`WARM_HARD_AGE`, under the calendar's 6); then it goes anyway. Reason "stale".
  - **No-shows.** A seat handed out (`GET /` without a cookie) whose visitor makes no request within 90 seconds (`NO_SHOW`) is reset: a link preview, a crawler or a monitor. Reason "no-show". The visit counts only once the visitor's first request reaches the seat (the pool's `visits_began`), so these aren't counted.
  - **Start again** (`POST /_seat/start`) frees the visitor's old seat at the next pass if their cookie still holds it (reason "left").
- **Seat processes** (`demo/seat_process.py`): each seat is `python -m optionsjourney` (the manager's own Python) with `BROKER_CREDENTIALS=demo`, `LISTEN_ON_NETWORK=no`, `PORT`, `DEMO_SEAT_TOKEN`, no `.env` (`PYTHON_DOTENV_DISABLED`) and only PATH, HOME, LANG and TZ from the environment. It runs in `<root>/seats/<n>/` (its data folder is `data/` there, emptied at each start whatever it holds, since the folder is the manager's; `seat.log` and the one before it, `seat.log.1`) in its own process group, so a stop takes the whole group: SIGTERM, 10 seconds, then SIGKILL and up to 5 seconds more. A seat still there after that stays on the manager's list, so the next pass tries again (and gives up after 30 seconds, logging it). Stopping the manager stops every seat at once: SIGTERM to all, one wait of 10 seconds in all, then SIGKILL for any left. Its pid and start time go in `pid`. At start-up the manager kills seats left by an earlier manager, but only a process that is still that seat: the same start time (`/bin/ps`, in the C locale), a seat's command line, leading its group, working in that seat's folder (`/usr/sbin/lsof`). If ps or lsof can't be run, nothing is killed.
- **Health:** the manager asks each seat's `/health` (with the seat's cookie) and `/demo/activity` (with the token in `X-Seat-Token`) for how long since its visitor did anything and the furthest tour step. Only a person counts as activity: opening a page (a GET that answers HTML and isn't an `/api/` call, the tour box's poll or a page fetched by a script, which browsers mark with `Sec-Fetch-Mode`) or sending anything (a form, a click). Open pages poll `/api/` on timers, so a forgotten tab still goes idle. A request the token check turned away (an earlier visitor's cookie, sent to `/_seat/ended`) never counts: only requests that passed the check set `g.seat_visitor`.
- **Cookies and routing.** Seating a visitor sets `oj_seat=<n>.<token>`; a queue place is `oj_wait`. Caddy (`packaging/demo/Caddyfile`) sends `/_seat/*` and `/stats` to the manager, a request with `oj_seat=<n>.` to seat n (WebSockets too; Caddy matches on the number only, `oj_seat=1.` never matches seat 10), and anything else to the manager. Every proxied request carries `X-Forwarded-Proto: https`, which Socket.IO needs to accept the page's `https://` Origin; Host passes through unchanged. When a seat doesn't answer (502/503), its visitor is sent to `/_seat/ended`.
- **The seat checks the token** (`web/routes/demo.py`): with `DEMO_SEAT_TOKEN` set, only a cookie carrying that token gets in; anything else is sent to `/_seat/ended` (Socket.IO gets a 403). So a cookie from before a reset, or a guessed seat number, gets nowhere.
- **The manager's pages:** `/` (seat, or the queue page `demo_seat_wait.html`, which polls `/_seat/wait` every 2 seconds), `/_seat/ended` (`demo_seat_ended.html`, with a button that posts `/_seat/start` to clear the cookie and start again; while the visitor's own seat is starting a new day, `demo_seat_restarting.html` instead: "Your demo is restarting…", back to `/` every 2 seconds), `/robots.txt` (turns every robot away; every manager page also says `X-Robots-Tag: noindex`), and `/_seat/health` (`{"assigned", "queued", "ready"}`, for this computer only: it is a 404 through Caddy, which adds `X-Forwarded-For`, and Caddy also answers it with a 404 itself). Any other page that reaches the manager (no seat cookie) is sent to `/`; an image or script there (`Sec-Fetch-Dest` other than `document`) gets a 404 instead, so it can't take a seat.

Trying it on a laptop, with Caddy installed:
```bash
uv run python -m optionsjourney.demo.manager --root /tmp/oj-seats --cap 2 --warm 1
PORT=8095 caddy run --adapter caddyfile --config packaging/demo/Caddyfile
curl -i -H 'Host: demo.optionsjourney.com' http://127.0.0.1:8095/
```
The cookies are Secure, so a browser on plain http won't send them back; use `curl -b 'oj_seat=…'`, or the tunnel.

## Counts
`demo/counts.py` keeps daily numbers in `<root>/counts.json`: visits (counted when the visitor's first request reaches their seat, with their wait if they queued), how many waited and their total wait, total time in seats, and how many visitors got to each tour step (8 = finished). No IP addresses, names, user agents or fingerprints. The file is written atomically after each change and keeps 90 days; a broken or missing file just starts again. `/stats` shows the last 14 days behind HTTP Basic auth with the password in `DEMO_STATS_PASSWORD` (any user name). Without the variable, `/stats` is a 404.

## Hosting (the prod Mac)
The demo runs on the always-on prod Mac behind its Cloudflare tunnel, like the site (decisions 0101 and 0102), under its own standard macOS user `ojdemo`, from that user's checkout of the public repo. `oj-demo install`, run by the admin from their own clone, writes three LaunchDaemons, so it starts at boot without anyone logging in:
- `com.optionsjourney.demo`: the seat manager (`.venv/bin/python -m optionsjourney.demo.manager --port 8096 --root ~ojdemo/.optionsjourney-demo`), Nice 10 so the trading app comes first (seats inherit it), restarted if it stops, 30 seconds to stop its seats (`ExitTimeOut`). Its plist holds `DEMO_STATS_PASSWORD` and is readable only by root.
- `com.optionsjourney.demo-proxy`: Caddy with `packaging/demo/Caddyfile` on `127.0.0.1:8095`.
- `com.optionsjourney.demo-update` (Nice 10, low-priority disk): every 5 minutes, `oj-demo update`, as `ojdemo`, fetches the public repo's `main`. When it moved, it waits until `/_seat/health` shows no one seated (or 30 minutes from when it first saw the commit), then checks it out (local changes in that checkout are discarded and logged; `oj-demo` manages it), runs `uv sync --frozen --no-dev` and stops the manager, which launchd starts again on the new code (Caddy too, if the Caddyfile changed). A failed `uv sync` goes back to the last commit and waits for the next one.

Logs are in `/Library/Logs/optionsjourney-demo/`: the folder is root's, the three log files are `ojdemo`'s, so it can write them but not swap them for links. Each seat's own log is `~ojdemo/.optionsjourney-demo/seats/<n>/seat.log`.

**The privilege rule.** `ojdemo` faces the internet, so nothing that runs as root (`install`, `start`, `stop`, `restart`, `status`, `logs`) executes, sources or reads anything `ojdemo` can write: its home, checkout, `.git`, venv, uv cache, state or logs. Root uses only system folders on its PATH (Homebrew's paths appear only inside the plists, for programs that run as `ojdemo`). `status` gets the live commit and a waiting update by running `git` and `cat` as `ojdemo` and shows their output only as cleaned-up text; `logs` runs `tail` as `ojdemo` and cleans each line; `install`'s `uv sync` runs as `ojdemo` and its output is shown only cleaned. Whatever runs as `ojdemo` gets no input (`</dev/null`). Nothing installed for the admin comes from `ojdemo`'s files either: `install` refuses to run from inside `ojdemo`'s home, or from a file or folder (the menu bar item's real path included, links followed) that isn't root's or the admin's, that others can write, or that has an access list (ACL) allowing anyone anything. It copies `oj-demo` to `/usr/local/libexec/optionsjourney-demo/oj-demo`, root-owned, in a folder it makes root's and refuses if any folder above it isn't root's alone (`/usr/local/bin` may be writable by an admin account or Homebrew, and the sudoers rule names this file). The menu bar item comes from the same clone. `tests/demo/test_packaging.py` checks this.

**The demo user's firewall** (decision 0103). `ojdemo` faces the internet and could otherwise connect to any service on this computer, the trading app included. `install` writes pf rules to `/etc/pf.anchors/optionsjourney-demo`: for connections `ojdemo` makes, on this computer only the demo's own ports (8095, 8096, 5101–5110); nothing at this computer's other addresses (pf's `self`, read when the rules load) or on private and link-local ranges (the home network, Tailscale's 100.64/10), except DNS to the resolvers `scutil --dns` listed at install; elsewhere only DNS (53), ssh (22) and https (443, the update job's git fetch and uv); everything else is refused. (The system's own lookups for git, curl and uv go through macOS's resolver, not as `ojdemo`; if the DNS servers change, run `install` again for tools that ask DNS themselves.) Replies to connections made to `ojdemo` (the tunnel to Caddy) pass. `install` doesn't turn pf on or edit `/etc/pf.conf`: it prints the steps, done once by the admin (below). `oj-demo status` shows `firewall: on` or `OFF`; `sudo oj-demo firewall-check <port>` checks pf is on with the rules loaded, that `ojdemo` reaches the seat manager, and that it can't reach `<port>` (give the trading app's port; it says when nothing listens there, since that proves nothing). Only curl's "couldn't connect" (exit 7, what pf's refusal gives) counts as blocked; any other failure is reported as "NOT blocked, or unclear" and the check fails. macOS loads `/etc/pf.conf` at boot but leaves pf off until something turns it on, so after a restart: `sudo pfctl -E` and the check again.

**Day to day:** `oj-demo status`, `start`, `stop` (stays stopped through a reboot until `start`), `restart` (ends every visit), `update`, `logs`, `firewall-check`. They run with sudo; the first four need no password, so the 🎓 menu bar item (SwiftBar: seats in use, ready and waiting, the live commit, the firewall) can run them. `oj-demo` isn't on the PATH (`/usr/local/libexec` isn't); an alias in your shell does it: `alias oj-demo=/usr/local/libexec/optionsjourney-demo/oj-demo`.

**One-time setup (the author), on the prod Mac:**
1. Close the trading account's home folder to other users, then make the demo user, a standard (not admin) account: `sudo sysadminctl -addUser ojdemo -fullName "OptionsJourney demo" -shell /usr/bin/false -password -`. To keep it off the login window: `sudo dscl . create /Users/ojdemo IsHidden 1`. Check it can't read the trading account's files: `sudo -u ojdemo ls ~<trading user>` should be refused.
2. `brew install caddy uv` (if not already there for the site).
3. The demo's checkout, which it runs and updates: `sudo -u ojdemo -H git clone https://github.com/optionsjourney/optionsjourney.git ~ojdemo/optionsjourney`
4. Your own clone, as your admin account, for installing: `git clone https://github.com/optionsjourney/optionsjourney.git ~/optionsjourney-demo-admin`
5. `sudo ~/optionsjourney-demo-admin/packaging/demo/oj-demo install` (never the copy in `~ojdemo`; install refuses it). It asks for the `/stats` password (Enter keeps the current one, `none` turns `/stats` off), syncs the app as `ojdemo`, copies `oj-demo` to `/usr/local/libexec/optionsjourney-demo/` (root-owned), writes the LaunchDaemons, the sudoers rule (checked with `visudo -c` first) and the firewall rules, copies the menu bar item if SwiftBar is set up, and starts everything. `oj-demo status` should show all three on and the seats answering. `OJ_DEMO_DRY_RUN=1 oj-demo install` prints what it would write and changes nothing.
6. Turn on the demo user's firewall, as `install` printed: add `anchor "optionsjourney-demo"` and `load anchor "optionsjourney-demo" from "/etc/pf.anchors/optionsjourney-demo"` to the end of `/etc/pf.conf`, then `sudo pfctl -nf /etc/pf.conf && sudo pfctl -f /etc/pf.conf && sudo pfctl -E`, then `sudo oj-demo firewall-check <the trading app's port>`. All its lines should end "as it should be".
7. Outside market hours: add `demo.optionsjourney.com` → `http://127.0.0.1:8095` to the prod tunnel's config above the final 404 rule, restart cloudflared, and route DNS for it as for the site (developer/site.md).

After `oj-demo`, the menu bar item or the LaunchDaemons change (the update job logs when `oj-demo` changed on main): `git -C ~/optionsjourney-demo-admin pull`, then `sudo ~/optionsjourney-demo-admin/packaging/demo/oj-demo install` again. Running `install` from the installed copy is refused, since it would only copy itself.

## Tests
`uv run pytest tests/demo`. They cover each module, the pages (the banner on every page, the switched-off features, the wording), the offline guard (in a subprocess, since it's never undone) and the runner. For seats: `test_seats.py` (the pool), `test_seat_process.py` (real seat processes, the slow ones), `test_seat_side.py` (the token check in a seat), `test_manager.py`, `test_counts.py`, and `test_packaging.py` (the Caddyfile's matchers, `oj-demo`'s syntax, its privilege rule, the firewall rules (parsed with `pfctl -n` where there is one) and its dry run). The run through Caddy is by hand, as above. The `demo_app` fixture builds an app with no background threads and puts the network back afterwards.
