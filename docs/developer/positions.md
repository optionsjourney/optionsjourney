# Positions

How orders become positions with P/L (`core/positions.py`). The rules, and where they differ from Tracker2, are in decisions [0017](../decisions/0017-positions-follow-tracker2.md) and [0020](../decisions/0020-matching-lessons-from-real-history.md).

```
OrderGroup (core/orders.py) ──build_positions──▶ Book(positions, unmatched)
```

`services/journal.load_journal` builds the book from **all** stored transactions, because a position can close months after it opens. It then attaches the user's edits and filters what the journal shows.

## Performance
- **Matching index:** matching only looks at positions that are still open, kept per account in `Book.open_in` (closed ones drop out of the index as they're found). Scanning the whole history for every close made building a year of trades take 17 s; with the index it takes under 1 s.
- **Cache:** `services.journal.PositionsCache` (one per app, on `Services`) keeps the built positions between page loads. It rebuilds only when the stored transactions change (row count or latest `updated_at`) or the set of split iron condors changes. Edits like names, tags and notes don't need a rebuild.
- **Dates (#284, decision 0111):** the filter row's date picker (`_journal_nav.html`, `js/date_range.js`; Tracker2's daterangepicker) replaces the status, period and date fields. Its presets are submit buttons named `preset`: `today` and `all` set the status (empty when it's the page's default), a key of `core/date_ranges.RANGES` (`yesterday`, `7d`, `14d`, `30d`, `month`, `last_month`, `ytd`) is kept as `Filters.range` so a saved view rolls on, and `custom` keeps `start`/`end`. `Filters.from_args` lets a preset replace the status, period and dates it came with. A range or dates make `shown_status` "all" (Tracker2: a date range shows open and closed), `opened_window(today)` gives the days `_matches` checks against the opening date, and `date_label` is what the button says. The old `status=open|closed` and `days` arguments are still read, so older links and dashboards work; the picker just doesn't offer them. The pages pass `date_ranges` and `today` (the app's New York date; the demo's is made up), which the calendar uses to mark today and shade a preset's days.
- **The filter row (#285):** `Filters.accounts` is a tuple of `broker:number` (the `account` argument repeated; `from_saved` also reads a dashboard's single account from before), used by `_matches`, the unplaced orders, `holdings.stock_holdings(accounts)`, `core/stock_history.share_moves`, `stock_transactions` and `trade_marks` (all `accounts=`), `services/stock_value.portfolio_value`; `/api/stocks`, `/api/stocks/value` and the stock chart read it through `_accounts_arg` (repeated or comma-joined). `js/filters_auto.js` submits the form on change (a dropdown's tick list when it closes; a click outside closes it; the date picker submits itself), so Apply is in `<noscript>`. A dashboard's **Save to "…"** shows only when `Filters.differs_from(dashboard.filters)`; **Delete dashboard** is a `link-button` (`filters__delete`).
- **Pagination:** the journal shows 100 trades per page and the Transactions page 200 rows (`web/pagination.py`). Summary stats always cover every trade that matches the filters.

## Split iron condors
`build_positions(orders, split=keys)` opens each iron condor whose key is in `split` as two positions, `…#put` and `…#call` ([0018](../decisions/0018-iron-condor-split-is-a-choice.md)). A closing order that covers legs of both halves is cut into its put and call parts, and each part closes its half (`_close_split_halves`). That's the one exception to "one close, one position". `Position.can_split` is true for an unsplit position whose opening order passes `core.structures.splits_by_type`: a sold and a bought put and call, one expiration, any quantities (#166, decision 0070); each half keeps its own units.

## The algorithm
1. **Batch:** orders are batched by broker order. The close half and the open half of one broker order belong together. Batches are processed oldest first. At the same moment, batches with opens go before closes, so a broker's correction pair nets out.
2. **Close or open:** each order in a batch is a close or an open:
   - The broker's open/close flag decides when it's there.
   - Expirations, assignments, exercises and maturities are always closes. A maturity (a Treasury bill paid out) is settled like an expiration, with close reason "Matured".
   - An unlabeled trade is a close if it offsets an open position, otherwise an open. Its legs are flipped first: an unlabeled buy is grouped as +long, but as a close it is closing a short.
3. **Roll:** if a batch is one close plus opens, and the close matches a position under the roll rules (whole legs, quantities dividing into the position's size, not 0DTE), the new legs join that position.
4. **Closes**, in this order:
   - **Unrecognized broker events** (`Kind.OTHER`, e.g. corporate actions) go straight to `book.unmatched`. They're never applied.
   - **Expirations, assignments and exercises** are settled leg by leg (`_settle`). Each contract's quantity settles the oldest open positions holding it, split across several if need be. Fills with no direction get one from the event (an assignment buys back a short, an exercise sells a long), and a contract's removal and cash-settlement rows are combined first (`_with_direction`).
   - **Closing trades** go to `_match`: the oldest open position that **every fill** fits (but a close a bot's exit sent tries that bot run's trade, or its split halves, first: `Book.owners`, from `journal.close_owners`, which maps each `bot_exits.broker_order_id` to its run's position key, #180) (`_allocate`: same contract, right direction, no more than is left). Failing that, both halves of a split iron condor are tried, then `_settle(completely=True)`, which spreads the order across several positions only if every contract fits. Anything else goes to `book.unmatched`.
5. **Opens:** each open starts a new `Position`, or two positions for a split iron condor.

Each batch runs inside a guard. If it raises, its orders go to `book.failed`, the error is logged, and everything else is still built.

## The numbers
- **Legs:** a `PositionLeg` keeps `opened`, `closed`, the opening and closing **cash** (`value`, + received) and the fees.
- **Realized P/L of a leg:** `(open_value − open_fees) × closed/opened + close_value − close_fees`, so a partial close books its share of the opening.
- **Realized P/L of a position:** the sum over all its legs, including legs closed by a roll.
- **Units:** how many whole copies of the trade its legs make, the largest number dividing every leg's quantity (`_units`): 3C:1P is 1, 6C:2P is 2, 3C:2P is 1 (#311, as Tracker2's closing price per unit). Not the smallest leg, which halves a 3C:2P trade's prices.
- **Entry price:** Σ(± price × quantity) of the opening fills ÷ units, with + for sold. A roll adds its own net price per unit.
- **Exit price:** the same, over the closing fills of the live legs ÷ units closed. For a fill without a price (an expiration or cash settlement) of an equity option, the cash amount ÷ 100 stands in.
- **Shares (#45):** one running position per stock per account. A single-leg share order (a buy, a dividend reinvestment, or shares from an assignment) joins an open position in the same account, stock and direction (`_add_to_running_stock`, an `ADD` event); shares inside a multi-leg order (a buy-write) don't. Before adding, the leg banks what it has realized and carries the shares still held at their average cost (`PositionLeg.bank`), so earlier sales keep their P/L and the events still add up. Selling all the shares closes it; the next buy starts a new one.
- **Status:** `closed` when every live leg is fully closed, `partial` when some quantity is closed, `open` otherwise. `close_reason` comes from the last event: Closed, Expired, Assigned or Exercised.
- **Waiting on the broker:** `awaiting_expiration(now)` is true when every leg still held is an option past its expiration close (16:00 New York time, `core/market.expiry_close`). The position stays open until the broker's expiration record arrives; the journal shows it as "Expired, waiting on broker". `core/expiry.estimate_expiration` estimates its P/L from closing prices (intrinsic value at the close, ×100), returning None for monthly AM-settled SPX/NDX/RUT, in-the-money stock options and futures options. The estimate's closes come from `services/expiry_prices.official_closes` (official closes only), through `services/market_data.CloseCache`: TastyTrade's final close or prev-close first, then Schwab's history for what's left, at most 3 seconds of Schwab per page; a close no broker has is asked again after 5 minutes. Found closes are cached for the life of the app, and estimates are shown, never totalled.
- **Settled at the close (#147, decision 0062):** when the user turns it on, `services/expiry_settle` runs 15 minutes after each session's close (a daemon thread started next to the P/L Day snapshots, checking every 5 minutes). It syncs first unless every account holding a leg that expires that day (`_expiring_accounts`) has `sync_state.synced_through` after the close (other accounts don't count; nothing expiring ends the day's run). An expiring account that still hasn't synced after that waits on its own (#185): its trades are left out and listed as skipped (`UNSYNCED`), the run isn't done, and it's retried until 8 PM, so a broker that can't sync (Schwab logged out) never holds up another account's settlements. It then calls `core/expiry.settle_expiring` on the synced accounts' positions of the unsplit book with the prices from `services/expiry_prices.prelim_prices` (the day's last price from either broker, or the official close when it's already out; `core/expiry_prices` never uses a price of zero or below) and the contracts of `book.unmatched`. The result is stored in `expiry_settlements` (one row per account, contract, direction), and the run's skips in the `expiry_settle_last_run` setting (JSON), read by the job only (decision 0109: no longer shown); the switch is the `expiry_settle_on` setting, in `core/settings.py`'s Syncing your trades section (Settings page). A sync that raises is logged; accounts that synced since the close settle anyway. A run is done for the day unless the sync failed or a close was missing, which are retried until 8 PM. When positions are built, `core/expiry.with_settlements` adds each stored settlement as an expiration fill (transaction id `app-settled:…`, value = ±intrinsic × qty × 100, fee = TastyTrade's $5 on one ITM leg) unless the account already has a broker expiration, assignment or exercise of that contract. `settled_by_app(position)` marks trades still closed by one, and the journal's `settled_prelim` (#186) marks those with a settlement fill whose row is still `prelim` (matched by broker, account and `settlement_fill`'s transaction id, since two accounts settling one contract share that id; its description says "(prelim)"), shown as "Settled at close (prelim)" with the price and its source in the tooltip (`prelim_note`). Each row also records how sure the price is (#186): `status` (`prelim` for a quick 4:15 price still to be corrected, `final` for the official close; rows from before are `final`), `price_source` (where the price came from), `prelim_close` (the first price, kept when prelim), `finalized_at` (when a correction replaced it) and `broker_alerted_at` (when the user was told the broker's own record differs). Corrections and the like raise unread alerts in `app_alerts` (`services/app_alerts`: one row per `dedupe_key`, so an event never alerts twice; each new alert is also sent through the notification channels, and a registered `on_change` callback runs after a new alert or a mark-as-read, and `on_new` gets each new alert, which `web/sockets.py` pushes as `alert_fired` for `js/trade_toasts.js` to pop up (#275); the Alerts page and the bell's list (`GET /api/alerts/recent`, the newest 15; `js/alert_bell.js`) mark read only the alerts they show, with `mark_read`; the bell's top section leaves out fired user alerts, which it lists as new alerts. A price or trade alert that goes off is stored here too, as kind `user_alert` with `send=False`, so it counts as new until seen. The bell's number is these unread alerts plus the system alerts at level `problem`: decision 0105). The 4:15 run itself raises no alert (decision 0106): only a correction or a broker record that differs does. The positions cache key includes the table's count, its latest `created_at` and `finalized_at`, and the count of `final` rows, so every correction rebuilds it (whatever the clock says). **The correction pass** (`correct_prelims`) runs on the same 5-minute loop, right after the day's run and whether or not the switch is on: each prelim row is corrected until 8 PM New York on the next trading day (`core/sessions.next_session_after`), after which it stays prelim. A prelim row whose contract already has the broker's own record is left prelim, so the broker check below compares that record with the P/L the user saw. It asks `services/expiry_prices.official_closes` for only those rows' (underlying, expiration) pairs, and only rows whose official close is found are corrected (`close_price`, `status = final`, `price_source`, `finalized_at`); final rows are never touched. Pairs are corrected one at a time (the final-row count in the cache key rebuilds the cache between them), and the journal's P/L of each app-settled trade is read before and after each; a trade whose P/L moved by $1.00 or more (`core/expiry_prices.pl_changed`) gets one `correction` alert ("SPX closed at 5795, not 5790. P/L … → …."), keyed `correction:{position key}:{expiration}` so a restart never alerts twice. The "not …" names the prelim of the rows in that trade's account (`shown` gives each trade's broker and account), since accounts can settle in separate runs. If reading the P/L or raising an alert fails after the rows were committed final, they're put back to prelim (close, source and `finalized_at` as before) and the next check tries again. **The broker's record** (`alert_broker_records`) is checked after each sync, on the thread that records trade events (`web/sockets.py`), and on the same 5-minute loop. For each contract (broker, account, symbol) with settlements not checked yet (`broker_alerted_at` empty) and a synced broker expiration, assignment or exercise, it compares the cash of the app's settlements (both directions) with the cash of the broker's rows (a cash settlement's two rows added together), with fees left out on both sides. A difference of $1.00 or more gets one `broker_record` alert ("SPX Short Put: your broker's record differs", "Settled by the app: -$450.00. Your broker: -$500.00."), keyed `broker:{lowest row id}`, named after the journal trade holding the broker's fill (else the contract). An in-the-money Schwab settlement (app cash not zero) isn't compared: the synced Schwab history only has $0 "Removed due to Expiration" rows, and its cash settlement isn't read yet (#187), so it would wrongly read as $0. Either way `broker_alerted_at` is set on the contract's rows, so each is checked once; all of a check's rows are marked in one commit at the end (each settlement commit wakes the journal's watcher, which runs this check again), and a module lock lets only one check run at a time (another returns 0 at once). Only the fills are read until some contract has a broker record to compare; the book is built only then, for the trade's name. Migration 0045 marks the settlements from before it as already checked, so upgrading never alerts about old trades.
- **P/L Day closes (#193):** without a snapshot, `services/pl_day.previous_closes(clients, symbols, today, now)` caches each symbol's previous close for the day (`_closes`; its lock is never held across a broker call). TastyTrade's market data comes first; options it didn't price fall back to Schwab's `quotes()` (batches of 50, OCC symbols as is, `closePrice > 0`), but only when `core/pl_day.schwab_close_counts(today, now)`: Schwab's `closePrice` is the previous session's only during the trading day before 4:00 PM New York. A symbol counts as tried only once it's found or every broker asked answered; one whose call failed is asked again after `RETRY_AFTER` (2 minutes, `retry_at`). `forget_closes()` empties the cache for tests.
- **0DTE:** all the position's options expire on the day it opened (New York time).

## Events
The P/L calendar (`core/calendar.py`) is built from these events: `daily_pl` books each event's realized P/L on its New York date and counts a trade once, on the day it fully closes (won or lost on its whole P/L); other days a trade closed in part count it as a partial. `month_grid` lays a month out as Monday–Friday weeks with week totals (weekend P/L folds into its week) and shades each day against the month's best and worst day. The calendar's months add up to the journal's realized P/L. `equity_curve` turns the same days into cumulative P/L and drawdown (the high-water mark starts at zero, as in Tracker2), `max_drawdown` finds the deepest point, and `by_month` rolls it up for the table view. `realized_between` gives each trade's P/L booked between two days by the same rule, so the calendar drawer adds up to the cell it opened from; `MonthGrid.last` and `Week.start`/`end` (the week's days inside the month) are the ranges the cells open. The **P/L Calendar** view (`/metrics/calendar`, `templates/pl.html`, on the Metrics tab, `web/routes/metrics.py`; `/journal/pl` redirects) shows the calendar and the charts. Each in-month day carries its economic events (`services/economic_events.events_between`, as `day_items`). Clicking a day, a week's total or the month summary opens `_pl_drawer.html`: `static/js/pl_drawer.js` loads `GET /metrics/calendar/period?first=&last=` plus the page's filters (not `start`/`end`, which are the filters' opening dates; at most 31 days), which renders `_pl_period.html` from `services/journal.load_period`. That groups the period's trades by each dashboard (its tags, accounts and search, through `_matches`, with its status and dates cleared), puts the rest in Other trades, and keeps the total over distinct trades because dashboards overlap. Inside a group, `PeriodGroup.rows` folds trades with one name in one account into a `PeriodRow`, so a bot's entries are one expandable line. The view draws its charts with `web/static/js/line_chart.js` (shared with Account values and the bot page's P/L graph, whose `data-x="trade"` spaces points one per trade instead of by date): plain SVG, no chart library, so the app needs no internet for it.

The journal's summary (`core/stats.journal_summary`) follows Tracker2's `journal_service`: closed P/L leaves out what rolls realized on still-open trades; premium is the cash of the opening order plus rolls (no multipliers needed), split leg by leg for partly closed trades; per-lot figures divide by the position's units (closed lots for partials).

The trade list's order (`services/journal.py`): unsorted it's `open_then_closed` (open trades, then closed ones by closing day); a column heading uses `SORTS` through `sort_entries`. Everything ordered by when trades opened uses `opened_key` (#214, Tracker2's Opened sort): trades opened in the same minute group by entry (broker, account, bot name, underlying) before the exact time orders them, so two accounts' put and call sides opened seconds apart don't interleave, whichever way the list is sorted.

Live open P/L (`core/live.unrealized_pl`): per open leg, (open cash − open fees) × share still open + sign × mark × quantity left × multiplier (100 for options, 1 for shares; futures not yet). `/api/open-pl` (journal filters) subscribes the legs on the quote hub and returns each open trade's figure and the total. `web/static/js/open_pl.js` (a module; `plText` is tested in `tests/web/static/js/open_pl.test.js`) polls it every 5 seconds for the Open P/L box and the rows. A row's open P/L and P/L Day both show their % of the trade's premium beside them (`data-premium` on the P/L cell, `premium_of`), "+$30.00 (+15.0%)" (#213, Tracker2's P/L Day %); no premium, no %.

**After hours (#241, decision 0091; Tracker2's `leg_mark_snapshot.apply_closing_marks`):** the journal's open P/L, P/L Day, the Paper journal and the P/L Day snapshot read marks through `services/streaming.marks(hub, keys, now, strict=)`, not `quote.mark`. `core/quotes.no_market(quote)` is an option (OCC symbol) whose ask is at least `NO_MARKET_MIN_ASK` (0.50) and whose bid is missing or under half the ask; `quotes_are_the_market(now)` is 09:30 New York until 15 minutes after the session's close (`OPTIONS_TRADE_AFTER_CLOSE`). Outside that window `closing_mark` marks a no-market quote at the symbol's last real mark, else its own mark (or none with `strict`, so the snapshot never stores one). `QuoteHub.put` keeps each symbol's last mark from a quote that isn't no-market (`good_mark`, `good_marks`). `pl_day.take_snapshots` saves the open legs' good marks in `close_marks` (one row per symbol, migration 0049), and `pl_day.start` loads them into the hub (`seed_good_marks`, never over one seen since the start), so a restart after hours still has them.

Trading metrics (`core/metrics.py`) work from the same days plus each closed position's P/L and fees: `trade_stats` (win rate over all closed trades, break-evens included, used everywhere; expectancy, profit factor, average win/loss), `period_stats` per day, week (Monday start) or month, and `weekday_stats` for Monday to Friday. The page is `/metrics` (`web/routes/metrics.py`; `/journal/metrics` redirects), which shares its dashboard tabs and filters with the journal (`templates/_journal_nav.html`, whose view switch shows P/L Calendar and Trading metrics on `metrics.*` pages, Trades and Paper trades otherwise); its bars are drawn by `web/static/js/pl_bars.js`, each with `cumulative` (`_with_cumulative` in `load_metrics`) drawn as a line on a right-hand scale whose zero lines up with the bars' (`alignZero`).

`position.events` is the position's history: open, close, roll, expiration, assignment, exercise. Each event records the orders involved and the P/L it booked.

## Stocks tab (#236, #286)
Decisions [0092](../decisions/0092-stocks-performance-from-daily-saves.md) (the ticker drawer) and [0113](../decisions/0113-stocks-value-from-holdings-and-fills.md) (the cards, the value chart, Transaction History). The Stocks tab (`journal.kind == stocks`) shows three cards, a Portfolio value chart and two views. Nothing about it is stored: there is no stock table and no background job.
- **The cards:** `core/holdings.stock_summary(rows)` totals the priced `Holding`s (a row with no price is left out): `total_pl` and `total_pl_percent` (of the priced rows' cost), `market_value` (`Holding.market_value`, price × quantity) and `day_pl` with `day_pl_percent` (of market value less day P/L). The route's `_stock_summary` turns the totals into `None` ("—") while every held row is unpriced. `GET /api/stocks?account=` returns the rows and the `summary`; `static/js/holdings.js` refreshes the table and cards from it every 5 seconds.
- **The maths:** `core/stock_history.py` is pure.
  - `share_moves(fills, accounts)` turns the stock fills (`Kind.TRADE`, `ASSIGNMENT`, `EXERCISE`, `InstrumentType.STOCK`, the same ones `trade_marks` reads) into signed `ShareMove`s per New York day, account (`broker:number`) and ticker.
  - `held_by_day(today, moves, days)` works each (account, ticker) back from today's quantity: the quantity at day D's close is today's less the moves after D. A long is clamped at zero and a short at zero from the other side (a transfer or a split the fills don't explain); a clamp is logged at INFO, never shown. Accounts are then summed per ticker.
  - `value_series(held, closes, days)` gives a `ValuePoint` per day (value, `priced` of `total` tickers). A ticker with no close that day uses its latest close within `LOOKBACK_DAYS` (10) before, else it's left out of the value. Days before the first holding are dropped.
  - `stock_transactions(fills, accounts)` gives the same fills as `StockTransaction`s, newest first, with `action` Buy, Sell, Assigned or Exercised, the unsigned quantity, price, cash `value` and fees.
  - `RANGES` (1M, 3M, 1Y, All), `range_start` and `trade_marks(fills, ticker, accounts)` serve the drawer. Pass the ticker uppercased.
- **The value service:** `services/stock_value.portfolio_value(session_factory, clients, hub, accounts, now)` reads today's quantities with `holdings.kept_positions(strict=True)`: the same minute-old positions the Stocks page shows (#304; one broker round a minute for both, `strict` is `None` if any broker failed in that round); `None` (a broker didn't answer) returns no points and `COULD_NOT_LOAD`. The days are the trading days (`session_close`) from `first_day` (`sync.history_starts` read without a commit) to today. Fills come from `transactions.load_fills(since=fills_since(start))` (midnight New York). No tickers at all (nothing held, no stock fills) returns no points and no note, without fetching closes. `daily_closes` fetches each ticker's daily candles (`chart_market.price_history`, Schwab then TastyTrade) from `LOOKBACK_DAYS` before the start, cached for `KEEP_FOR` (an hour) per (ticker, start). A ticker whose closes fail is left out; when none can be priced the note is `NO_PRICES`. Once today's session has opened, today's point uses live prices from the quote hub (last, else mark) for the tickers held today that have closes (one with no closes stays out of today too, so the line doesn't step), keeping the last close for a ticker with no quote yet. Splits after the start aren't handled. A broker whose credentials say it was never connected (`NotConnected`, a kind of `CredentialsUnavailable`) is skipped rather than failing the strict read: `broker_positions(..., skipped=)` names it, and its fills are dropped before the walk-back.
- **Routes** (`web/routes/journal.py`): `GET /journal?kind=stocks&stocks_view=holdings|history` (anything else is Holdings). `history` loads the fills since the same first day as the chart (`stock_value.first_day` / `fills_since`) and passes `stock_transactions` as `stock_rows`; the filter form carries `stocks_view=history` so changing accounts stays on it. `GET /api/stocks/value?account=` returns `points` (`day`, `value`) and `note`; `static/js/stock_value.js` (a module; `plan(data)` is tested) fetches it after the page loads and draws it with `line_chart.js`, or shows the note, or with no points and no note hides the card. `GET /api/stocks/<path:ticker>/chart?account=&range=` (`path:` so BRK/B works) returns closes (any failure becomes the note "Prices aren't available right now."), the quantity and average cost per share of the same merged `Holding` the table shows, and the marks. It is 404 when the ticker isn't held in that scope, so Transaction History links only held tickers.
- **The drawer:** `_stock_drawer.html` and `static/js/stock_drawer.js` (opened by any `[data-stock-chart]` button) draw the SVG: the close line, the yellow dashed cost line, and ▲ and ▼ marks. A trade on a day with no close is left off.
